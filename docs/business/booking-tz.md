## Главное ограничение (не ломать ядро)

**Логика записи уже правильная** — её **не переписываем**.

Остаётся как есть в [booking.md](booking.md) / SPEC:

- тег `booking` → принимаю к себе; услуги, staff, слоты, instant `confirmed`;
- клиент → записаться / «Мои бронирования»;
- хозяин ведёт визит до «Оказана»; статусы, перенос, бонусы на услуге и т.д.

**Здесь другое:**

1. **Удобство** — как человек **быстро попадает** в уже существующие экраны (тег вместо тоггла/кэша; две линии на профиле, чтобы не забить UI).  
2. **Дополнение** — новые возможности для человека, которому **другие аккаунты дают заказы** (тег `bookingCalendar`, экран своих визитов). Это не «роль работника в иерархии», а просто сценарий того же равного аккаунта: «мне записывают».

```
Ядро booking          = не трогать (логика верная)
Удобство входа        = теги + линии кнопок на профиле
Новое для «мне дают»  = bookingCalendar + экран (read v1)
```

Слово «работник» в доках = **короткая метка линии UI** (верх), не должность и не подчинение.

## 1. Смысл и границы

**Зачем:** удобнее включать и открывать уже работающую запись через теги; добавить экран «мне дают заказы» для равного аккаунта с тегом `bookingCalendar`.

**Не является:**
- переписыванием логики слотов / статусов / create booking;
- иерархией «админ над работником» или отдельным типом бизнес-аккаунта;
- CRM / кассой / эквайрингом;
- бронью мест по схеме зала ([venue-seating.md](venue-seating.md));
- посещаемостью ([attendance.md](attendance.md)).

**Граница v1 этого ТЗ:** удобство входов (теги, две линии, без кэш-ярлыка) + новый контур `bookingCalendar` + паритет платформ.  
Happy path из [booking.md](booking.md) **сохраняем как есть**.

## 2. Участники (сценарии, не касты)

Все равны: один аккаунт может совмещать сценарии.

| Сценарий | Условие | Что делает |
|----------|---------|------------|
| **Хозяин точки** | тег **`booking`** | Услуги, staff, расписание, inbox, аналитика; CTA «Записаться» на своей витрине для гостей |
| **Исполнитель с календарём** | тег **`bookingCalendar`** | Видит аккаунты, которые дают заказы, и детали **своих** визитов |
| **Клиент** | авторизован, **без** этих тегов | Записывается к другим; **Мои бронирования** |
| **Гость на чужом профиле** | — | Видит «Записаться», только если у хозяина есть `booking` |

Staff в каталоге хозяина (имя или ник) — **данные слота**, не продуктовая «роль над».  
Кнопка календаря исполнителя появляется **только** от тега `bookingCalendar`, не от факта «меня добавили в staff».

## 3. Сущности (для ТЗ)

| Сущность | Смысл |
|----------|--------|
| Account-тег `booking` | Сила приёма записи к своему аккаунту |
| Account-тег `bookingCalendar` | Сила экрана «мне дают заказы» |
| Услуга / staff / расписание / booking | Как в [booking.md](booking.md) (без изменений смысла) |
| Связь staff ↔ `profile_id` | Откуда берутся «аккаунты-источники» для календаря исполнителя |

## 4. Слой тегов — требования

### 4.1 Ключи

| Ключ (EN) | Группа | Линия на профиле | Сила |
|-----------|--------|------------------|------|
| `booking` | account | **нижняя** (админ точки) | Приём записи |
| `bookingCalendar` | account | **верхняя** («мне дают») | Календарь чужих заказов на меня |

Подписи — только фронт ([localization-dictionaries.md](localization-dictionaries.md)).  
Новый ключ `bookingCalendar` — в каталог бэка + enum/catalog мобилки + web catalog.

### 4.2 Правила силы (обязательные)

| # | Правило |
|---|---------|
| T1 | Нет тега → нет кнопки этой силы и клиент **не** стартует связанные сценарии/запросы «на всякий случай» |
| T2 | Один тег = один набор сил; `booking` ≠ `bookingCalendar` |
| T3 | Тег выбирает сам пользователь в **Редактировать профиль** |
| T4 | Источник правды ярлыка хозяина — **тег с бэка**, не prefs / localStorage |
| T5 | RLS/RPC на бэке остаются обязательными; фронт-гейт не замена политике |
| T6 | Мобилка и сайт — одинаковые условия показа и смыслы экранов |

### 4.3 Две линии кнопок на своём профиле

Полный паттерн: [profile-service-shortcuts.md](../code/ui/profile-service-shortcuts.md).

| Требование | Деталь |
|------------|--------|
| Верх | силы работника (`bookingCalendar`, …) |
| Низ | силы админа точки (`booking`, …) |
| Плотность | в линии ≤2 → иконка + текст; ≥3 → только иконка |
| Пусто | линия не рисуется |
| Не сюда | «Мои бронирования» клиента — в ⋯ / меню |

## 5. Жизненный цикл (с тегами)

### 5.1 Хозяин (`booking`)

| Фаза | Как |
|------|-----|
| Создать / включить | Edit profile → тег `booking` → сохранить на бэк |
| Активировать | Появилась кнопка на **нижней** линии + доступ к хабу записи |
| Действовать | Услуги, staff, расписание; принимать записи; вести визит до «Оказана» |
| Учитывать | Inbox + аналитика |
| Выключить | Снять тег `booking` → кнопки/CTA хозяина пропадают; данные каталога на бэке не обязаны удаляться в v1 |

### 5.2 Исполнитель (`bookingCalendar`)

| Фаза | Как |
|------|-----|
| Подключить данные | Хозяин добавил человека в staff по нику (`profile_id`) — как сейчас |
| Включить силу | Edit profile → тег `bookingCalendar` |
| Активировать | Кнопка на **верхней** линии |
| Действовать | Открыть экран: список аккаунтов-источников → свои заказы / деталь |
| Учитывать | Только свои визиты (staff-scoped) |
| Выключить | Снять тег → кнопки нет; привязки staff у хозяев остаются |

Пустой список источников при включённом теге — **норма** (показали экран, данных ещё нет).

### 5.3 Клиент (без тега записи)

Как в [booking.md](booking.md): чужой профиль / пост → записаться → **Мои бронирования** → отмена/перенос в окне правил.  
Теги `booking` / `bookingCalendar` **не требуются**.

### 5.4 Визит (хозяин ведёт)

Без изменения смысла статусов из [booking.md](booking.md): confirmed → … → «Оказана» только вручную.

**v1 календаря исполнителя:** просмотр (read). Смена статусов визита с экрана `bookingCalendar` — **вне скоупа v1** (фаза позже).

## 6. Карта экранов и входов

### 6.1 Входы

| Вход | Условие | Куда | Платформы |
|------|---------|------|-----------|
| Нижняя линия профиля → запись | тег `booking` | Хаб / inbox хозяина | mobile + web |
| Верхняя линия → календарь заказов | тег `bookingCalendar` | Экран источников + заказы | mobile + web |
| Настройки → Запись | тег `booking` | Тот же хозяинский контур | mobile + web |
| ⋯ / меню → Мои бронирования | авторизован | Клиентский список | mobile + web (паритет явного входа) |
| Чужой профиль → Записаться | у хозяина `booking` | Client book flow | mobile + web |
| Пост с услугой → CTA | услуга активна + хозяин с `booking` | Book flow с выбранной услугой | mobile + web |

### 6.2 Новые / меняемые экраны

| Экран | Действие ТЗ |
|-------|-------------|
| Свой профиль — блок 2 линий | **Новый** shared-паттерн (или довести) |
| Хаб / inbox хозяина | Гейт по тегу `booking`; убрать зависимость от тоггла-кэша |
| Экран `bookingCalendar` | **Новый:** список аккаунтов → список/календарь своих заказов → деталь (read) |
| Мои бронирования | Вынести/сохранить вход **вне** гейта `booking` на сайте |
| Edit profile — теги | Добавить выбор `bookingCalendar` |

## 7. Таблица решений (зафиксировано)

| Тема | Решение |
|------|---------|
| Иерархия ролей | Нет; только теги и сценарии |
| Ярлык хозяина | Только тег `booking` с бэка; prefs/localStorage ярлыка — убрать |
| Календарь исполнителя | Отдельный тег `bookingCalendar` |
| Показ кнопки календаря | Только тег, не «факт staff» |
| Данные календаря | Staff с `profile_id` = я; только свои визиты |
| v1 календарь | Read-only |
| Клиентский список | Без тега; явный вход на mobile и web |
| Плотность кнопок | ≤2 icon+text; ≥3 icon only; по линии |
| Раскладка | Верх = работник; низ = админ точки |
| Паритет | Mobile = web по смыслу |
| Правда UI vs бэк | Фронт режет UI/запросы; RLS всё равно |

## 8. Сеть / sync / сессии

| Тема | Решение |
|------|---------|
| Источник тегов | Профиль с бэка после edit / load профиля |
| Offline ярлык | Не хранить отдельный «shortcut on» в prefs |
| Logout / смена аккаунта | Теги и кнопки только от нового профиля |
| Несколько устройств | Одинаково: тег на сервере |
| Календарь / inbox | Online; без offline-outbox в v1 этого ТЗ |

## 10. Вне скоупа (явно)

- Переписывание ядра записи (слоты, статусы, create booking) — логика уже верная
- Иерархия «админ управляет работником» как продуктовая роль
- Смена статусов визита с экрана `bookingCalendar` (v1 = только смотреть)
- Полный доступ исполнителя к услугам / аналитике / ценам точки
- Удобства для staff **только по имени** (без Clover-аккаунта)
- Автопоказ календаря без тега `bookingCalendar` (только потому что добавили в staff)
- Один тег на оба сценария (`booking` ≠ календарь чужих заказов)
- Ярлык хозяина только в device cache
- Эквайринг, отзывы, venue-seating
- Функционал только на одной платформе

## 12. Критерии приёмки

### Теги и профиль
- [ ] Можно включить `booking` и/или `bookingCalendar` в edit; после save кнопки появляются на нужной линии  
- [ ] Снятие тега убирает кнопку без перезапуска приложения (после обновления профиля)  
- [ ] 1 кнопка в линии — с текстом; 3+ в линии — только иконки  
- [ ] Пустая линия не занимает место  

### Хозяин
- [ ] Нет ярлыка из prefs/localStorage; только тег  
- [ ] Без `booking` нет CTA «Записаться» на витрине и нет хозяинского хаба с профиля  
- [ ] С `booking` — запись/inbox/услуги работают как в [booking.md](booking.md)  

### Исполнитель
- [ ] Без `bookingCalendar` нет верхней кнопки, даже если есть staff-привязки  
- [ ] С тегом — экран открывается; видны только свои заказы / источники  
- [ ] v1: нельзя менять статус визита с этого экрана  

### Клиент
- [ ] «Мои бронирования» доступны без тегов записи на **mobile и web**  

### Паритет
- [ ] Те же условия показа и те же смыслы экранов на обеих платформах

## 14. Схема одной картинкой

```
Edit profile
  ├── +booking            → нижняя линия → хозяин (inbox / услуги)
  ├── +bookingCalendar    → верхняя линия → источники → мои заказы (read)
  └── (без тегов записи)  → ⋯ Мои бронирования (клиент)

Чужой профиль: CTA Записаться ⟺ у хозяина есть booking

Правда ярлыка = тег на бэке. Prefs shortcut = нет.
Линии: ≤2 icon+text · ≥3 icon. Mobile = web.
```
