# Локализация и справочники (как устроено)

**Статус:** правило продукта / архитектуры данных  
**Связано с:** [profile-data.md](profile-data.md), [catalog-sync.md](catalog-sync.md)

---

## Главное правило

| Слой | Что хранит |
|------|------------|
| **Бэкенд (Supabase / БД)** | Только **английские ключи** (slug / code). Без переводов. |
| **Фронт (Flutter)** | Все **переводы и подписи** для UI. Для справочников — **enum’ы**. |

Бэк **не** держит строки вроде «Алматы», «Красота», «Казахстан».  
Бэк держит только ключи: `almaty`, `beauty`, `kz`.

Весь перевод приложения (русский и дальше другие языки) живёт **на фронте**.

---

## Какие данные так устроены

Справочники «фиксированный набор вариантов»:

- страны (`country_code`);
- города (`city_code`);
- теги (`marker_tags.key` — профиль, маркеры, фильтры);
- статусы-enum в БД, где значение — английское слово (`active` / `inactive`, `active` / `hibernate`).

По смыслу это **массив (набор) английских слов-ключей**, а не локализованный текст.

Свободный пользовательский текст (имя, био, ник) — другое: его пишет человек, бэк хранит как есть. Это **не** справочник и **не** переводится системой как enum.

---

## Как хранится на бэке

1. В таблицах-справочниках и в колонках профиля — поле **code / key** на английском (латиница, camelCase или lower slug — как уже принято в схеме).
2. **Нет** колонок `name_ru`, `title_en`, `label_*` для этих справочников как источника UI-текста.
3. API отдаёт клиенту ключ (`kz`, `beauty`, `booking`).
4. Если ключ неизвестен фронту — UI может показать сырой ключ или скрыть, но бэк не «подскажет» перевод.

Пример хранения:

```
profiles.country_code = "kz"
profiles.city_code    = "almaty"
profile tag key       = "salon"   -- через marker_tags + profile_tag_links
```

Не так:

```
country_name = "Казахстан"   ❌ для справочника
city_name    = "Алматы"      ❌
```

---

## Как это на фронте

1. Для каждого такого справочника — **enum** (или аналог с фиксированными значениями).
2. У значения enum:
   - **ключ** = то, что пришло с бэка / уйдёт на бэк;
   - **подпись** = перевод для текущего языка UI (сейчас в основном `labelRu`).
3. Смена языка приложения = смена подписей на фронте, **без** миграций и без новых колонок на бэке.
4. Новые языки = новые строки/ресурсы на фронте, не таблицы переводов в Supabase для этих справочников.

Пример мысли:

```
CountryCode.kz  → code: "kz",  label: "Казахстан" (на фронте)
CityCode.almaty → code: "almaty", label: "Алматы" (на фронте)
MarkerTagKey.salon → "salon" / "Салон"
```

## Запомнить для команды

| Вопрос | Ответ |
|--------|--------|
| Где перевод UI справочников? | Только фронт |
| Что на бэке у стран/городов/тегов? | Английские ключи |
| Как фронт моделирует справочник? | **Enum** (+ подпись для языка) |
| Нужны ли `*_ru` колонки на бэке для справочников? | **Нет** |
| Био и имя пользователя? | Свободный текст, не enum |

## Связь с профилем

## Коротко

```
Бэк:   ["kz", "almaty", "beauty", "booking", "active"]   ← только ключи
Фронт: enum + перевод для пользователя                 ← весь UI-текст
```
