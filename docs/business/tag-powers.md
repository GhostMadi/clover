# Сила тегов профиля (tag powers)

**Статус:** черновик процесса (глобальная фича)  
**Связано с:** [profile.md](profile.md) · [profile-data.md](profile-data.md) · [booking.md](booking.md) · [booking-staff-plan.md](booking-staff-plan.md) · [catalog-sync.md](catalog-sync.md) · [localization-dictionaries.md](localization-dictionaries.md)

Перед реализацией новой силы — [_feature-lifecycle-checklist.md](_feature-lifecycle-checklist.md).

---

## Зачем

**Тег на профиле** — не только подпись на витрине. У выбранного account-тега есть **сила**:

1. **Визуал** — какие кнопки / блоки / акценты показывать (без тега элемент **не рисуем**).  
2. **Поведение клиента** — какие запросы и сценарии запускать (тег = «пользователю нужны эти функции»).

Это **глобальный паттерн** для уже существующих фич (привести к одной логике) и для будущих.

Конкретный список тегов и их сил **сейчас не фиксируем** — теги будут добавляться по мере продукта. Сначала договариваемся о правилах.

Ориентир: тег `booking` — приём записи; тег `bookingCalendar` — календарь заказов, которые дают другие.  
План: [booking-staff-plan.md](booking-staff-plan.md) · **ТЗ записи:** [booking-tz.md](booking-tz.md).  
Посещаемость: `attendance` (admin) + `attendanceWork` (worker) · **ТЗ:** [attendance-tz.md](attendance-tz.md).  
Ресурсы: тег **`resources`** (admin only) — местоположения и фильтры витрины; без prefs-ярлыка.

## Участники / роли

| Роль | Что делает |
|------|------------|
| Владелец профиля | В **Редактировать профиль** выбирает теги из списка справочника |
| Гость | Видит на чужом профиле только то, что разрешено тегами хозяина (кнопки, CTA) |
| Клиент приложения | По набору **своих** тегов показывает/прячет свои экраны и дергает нужные API |
| Clover (продукт) | Один тег → один понятный набор сил; без «скрытой магии» без тега |

## Сущности

| Сущность | Смысл |
|----------|--------|
| **Account / power-тег** | Ключ из справочника, висит на профиле и **включает супер-силу** |
| **Определение силы** | Два общих контейнера: **`admin`** и **`worker`** (`marker_tags.group_key`) |
| **Сила тега** | Пара: визуальные проявления + какие функции/запросы доступны |
| **Каталог тегов** | Список для edit; подписи только на фронте |

### Два определения (супер-фичи)

Все силовые теги живут **внутри** одного из двух определений. Это **не иерархия людей**, а тип силы:

| Определение (`group_key`) | Смысл | Линия на профиле | Примеры тегов |
|---------------------------|--------|------------------|---------------|
| **`admin`** | Мажорные сервисы хозяина точки: «я веду» | **Нижняя** | `booking`, `attendance`, `resources`, … |
| **`worker`** | Доп. функции исполнителя: «мне дают / я участвую» | **Верхняя** | `bookingCalendar`, `attendanceWork`, … |

Новый силовой тег **обязан** попасть в `admin` или `worker`.  
Витринные/маркерные группы (`who`, `type`, `place`, …) — **другой** контур, не силы.

Маркерные теги постов/карты — фильтры контента. Этот процесс — про **силы профиля**.

## Правила (зафиксировано)

| Тема | Решение |
|------|---------|
| Scope тегов | Силовые теги профиля в группах **`admin`** / **`worker`**. Конкретные ключи — **по мере появления** |
| Один тег | **Один тег = свой набор сил**. Не собираем «силу» из нескольких тегов в один сложный коктейль |
| Определение | Тег всегда в одном определении: admin **или** worker (не оба) |
| Кто выдаёт | Пользователь **сам выбирает** из списка при редактировании профиля |
| UI | Нет тега → нет кнопки / блока; линия профиля = определение (worker сверху, admin снизу) |
| Запросы | Клиент смотрит теги → решает, **какие** сценарии и вызовы бэка открывать |
| Правда v1 | **Фронт** управляет показом и тем, какие запросы слать. Список тегов приходит с профиля / edit |
| Бэк | Не ослаблять: даже если кнопка спрятана, **RLS / RPC** по-прежнему решают, можно ли действие. Фронт не замена политике |
| Справочник | Ключ EN на бэке; enum + подпись на фронте ([localization-dictionaries.md](localization-dictionaries.md)) |

## Два слоя силы

```
Тег на профиле
├── Определение
│     admin  → нижняя линия профиля (мажорные сервисы)
│     worker → верхняя линия (доп. функции)
├── Визуал
│     кнопки по линии; плотность ≤2 / ≥3:
│     см. [profile-service-shortcuts.md](../code/ui/profile-service-shortcuts.md)
│     + CTA на чужом профиле, бейджи, секции настроек / хабов
└── Функции
      какие экраны открывать, какие repo/RPC вызывать
```

| Если есть тег… | Определение | Цвет (сервис) | Визуал | Функции |
|----------------|-------------|---------------|--------|---------|
| `booking` | admin | жёлтый **Запись** | нижняя «Запись», CTA «Записаться» у гостя | услуги, inbox, create booking… |
| `bookingCalendar` | worker | жёлтый **Запись** (тот же сервис) | верхняя «Календарь» | источники заказов + свои визиты (read) |
| `attendance` | admin | синий **Посещаемость** | нижняя «Управление» | create company, invite, табель… |
| `attendanceWork` | worker | синий **Посещаемость** | верхняя «Посещаемость» | punch + worker-хаб |
| `resources` | admin | сирень **Ресурсы** | нижняя «Ресурсы» | местоположения, фильтры витрины |
| будущий тег | admin **или** worker | цвет **своего** сервиса ([AppServiceKind](../../lib/core/resources/app_service_accent.dart)) | кнопка в нужной линии | свои запросы |

Чипы на **своём** профиле / в edit / в селекторе: силовые теги красятся акцентом сервиса.  
На **чужом** профиле силовые теги **не показываем** (витринные who/type/… — можно).  
Витринные без `serviceKind` — нейтральный бренд.

Новый тег = ключ + определение admin/worker + **привязка к сервису (цвет)** + сила на фронте + (при необходимости) политики на бэке.

## Жизненный цикл

| Фаза | Как |
|------|-----|
| Выбрать тег | Edit profile → мультивыбор из справочника → сохранить |
| Активировать силу | После сохранения профиль отдаёт теги → UI и клиентские гейты пересобираются |
| Действовать | С тегом: видны кнопки, идут нужные запросы. Без тега: UI пустой по этой силе, лишние запросы не шлём |
| Снять тег | Убрал в edit → силы пропадают с витрины и из клиентских гейтов |
| Новый тег в продукте | Ключ в справочнике → enum/catalog → описание силы (визуал + функции) → стык с фичей |

## Карта экранов (где живёт)

| Экран | Роль тегов |
|-------|------------|
| Edit profile → теги | Выбор |
| Свой / чужой профиль | Визуал шапки, CTA гостя |
| Настройки / хабы сервисов | Пункты меню по силам |
| Фичи (запись, …) | Гейт входа в сценарий + какие API дергать |

---

## Стыки → решения

| Тема | Решение |
|------|---------|
| Уже есть `booking` | Первый эталон силы; привести остальные гейты к тому же паттерну |
| Будущие фичи | Не плодить «особые флаги» в обход тегов — новая capability через **тег + сила** |
| Конфликт визуалов | Один тег — один набор; при нескольких тегах силы **складываются** (кнопки union), без приоритета «кто красивее» в v1 |
| Гость без тега у хозяина | Не видит CTA этой силы |
| Web и мобилка | Тот же ключ тега и та же идея силы; UI может отличаться |

---

## Сеть / sync

- Теги профиля читаются вместе с профилем (как сейчас `account_tags`).  
- Смена тегов — через edit profile → sync link на бэке.  
- Клиент **не** шлёт «лишние» запросы модулей, если тега нет (экономия и ясный UX).

---

## Не сейчас

- Жёсткий закрытый список всех будущих тегов в этом файле  
- Админская выдача тегов «вручную» без edit profile  
- Сложные формулы «2 тега = 1 суперсила»  
- Только-клиентская «безопасность» без RLS (запрещено правилами гармонии)

## Коротко

```
Edit profile → выбирает теги (секции Админ / Worker)
        ↓
Определение: admin | worker → линия на профиле
        ↓
Один тег → свой визуал + свои функции/запросы
        ↓
Нет тега → нет кнопки, не зовём ненужный бэк
        ↓
Список тегов растёт; определения admin/worker — общие для всех сервисов
```
