# Бронь / билеты по пространству

**Статус:** **моки** — мобилка смотрит; рисовалка продуктово в **Ресурсах → Схемы**; legacy-мок ещё может жить под `/app/settings/venue` до редиректа (см. [space-plan-tz.md](space-plan-tz.md) WP1)  
Веб-редактор поддерживает **несколько этажей** (вкладки): у каждого свой план `nodes`.  
**Где живёт схема как справочник:** [space-plan-resources.md](space-plan-resources.md) — тип в **Ресурсах** (`space_plans`); при create заведения/точки — опц. присвоение, как `location`.  
**UI-имя:** **«Бронь»** · тег профиля **`venue`** (пока не в каталоге — вход из Настроек без тега)  
**Для кого:** продукт / бизнес / дизайн  
**Не про:** SQL, RPC, canvas-SDK  

**Не путать с [booking.md](booking.md) — «Запись»:**

| | **Запись** | **Бронь** (этот док) |
|--|------------|---------------------|
| Смысл | Услуга + время + мастер | Место / билет / доступ к пространству или событию |
| Пример | Стрижка, консультация | Стол, кресло в зале, билет на сеанс, зона на плане |
| Создание | Сразу подтверждено | Сначала **запрос** → решает хозяин |
| Рисование | Нет | Опционально: схема пространства «как в Figma» |
| Где рисуем | — | **Только сайт** (тяжёлый редактор) |
| Где смотрим / бронируем | Мобилка + веб | Мобилка + веб |
| Тег | `booking` | `venue` |
| Inbox | Свой | **Свой** (не смешивать) |

Один аккаунт может иметь **и запись, и бронь** — два сервиса рядом.

Связано: [profile.md](profile.md) · [settings.md](settings.md) · [publications.md](publications.md) · [chats.md](chats.md) · [notifications.md](notifications.md) · [features-catalog.md](features-catalog.md) · [website.md](website.md) · [space-plan-resources.md](space-plan-resources.md)

## Зачем (продуктовая идея)

Clover даёт **любым предприятиям** продавать и принимать бронь на **свои места и события** — от простого билета до полного плана зала.

Не маркетплейс «все залы Казахстана». Discovery как у записи: **профиль, пост, карта, диплинк**.  
Кто хочет — входит: кафе, кино, театр, коворкинг, концерт, ярмарка, парковка на плане, своя раскладка.

**Оплаты в Clover пока нет.** Клиент шлёт **запрос**; хозяин подтверждает вручную. Ценность v1 = **ясная схема + заявки + inbox**, не касса.

## Лестница сложности (все входят на своём уровне)

Хозяин **не обязан** рисовать. Три режима одного сервиса:

| Уровень | Что делает хозяин | Что видит клиент | Кому подходит |
|---------|-------------------|------------------|---------------|
| **A. Простые билеты** | Каталог билетов / тарифов без схемы | Список: «Стандарт», «VIP», сеанс | Концерт, лекция, вход |
| **B. Список мест** | Объекты брони строками (стол 1, кресло A12) без рисунка | Список (свободные сверху) | Быстрый старт ресторана / зала |
| **C. Схема пространства** | Рисует план «как в Figma» на **сайте**; помечает что бронируется | Схема + опционально список | Ресторан, кино, театр, свой зал |

**Правило:** объект брони один (тот же id) в списке и на схеме. Схема — надстройка, не другой каталог.

Можно начать с A или B и **позже** нарисовать план и привязать те же bookable к фигурам.

Веб-мок кабинета: хаб заведения → **Места** · **Сеансы/слоты** · **План** · **Витрина** · **Inbox** (связки без бэка).

## Рисование пространства («как Figma»)

### Где

| Действие | Платформа |
|----------|-----------|
| Создать / править план, фигуры, bookable, сеансы | **Только веб-кабинет** (сайт) — вход продуктово: **Ресурсы → Схемы** ([space-plan-resources.md](space-plan-resources.md)); сейчас мок ещё под `/app/settings/venue/.../plan` |
| Смотреть схему, запросить бронь, inbox на ходу | **Мобилка + веб** |

Рисуем **только на сайте** → публикуем JSON плана → **мобилка и веб только смотрят** и кликают bookable. Править схему с телефона v1 нельзя.

### Что можно рисовать

Стены, двери, проходы, сцена, бар, столы, кресла, зоны, подписи, цвет, слои, этажи.  
Хозяин **сам** задаёт смысл: «стол у окна», «ряд 3», «ложа», «зона фудкорта».

Любая фигура (или группа) может стать **объектом брони** (bookable): capacity, цена-ориентир, подпись.  
Декор без флага bookable — только картинка, не кликается.

Нет шаблона «только кино»: сетка рядов — **помощь** редактора позже (V2), не обязательство.

### Публикация

Клиент видит только **опубликованный** план. Черновик на сайте не ломает витрину.  
Смена раскладки → **версия плана**; старые брони хранят snapshot места.

### JSON: как хранится рисунок (и как его видит клиент)

Полный пример: [`venue-plan.full.example.json`](venue-plan.full.example.json) · контракт AI: [`venue-plan-json.md`](venue-plan-json.md).  
Короткий product: [`venue-plan.example.json`](venue-plan.example.json).

Идея в двух слоях:

1. **План (геометрия)** — что нарисовал хозяин на сайте (`nodes` + стили).  
2. **Inventory (занятость)** — `free` / `held` / `taken` на `bookable_id` для выбранного сеанса/слота.  
   Состояние **не** пишется внутрь фигуры навсегда — подмешивается при отдаче клиенту.

```json
{
  "plan": {
    "id": "plan_floor1",
    "version": 3,
    "status": "published",
    "canvas": { "width": 1000, "height": 800 },
    "nodes": [
      {
        "id": "n_bar",
        "kind": "rect",
        "role": "decor",
        "label": "Бар",
        "frame": { "x": 80, "y": 60, "w": 840, "h": 90 },
        "bookable_id": null
      },
      {
        "id": "n_table_2",
        "kind": "rect",
        "role": "bookable",
        "label": "2",
        "frame": { "x": 420, "y": 220, "w": 220, "h": 180 },
        "style": { "fill": "#FFA39E", "radius": 14 },
        "bookable_id": "bk_table_2"
      }
    ]
  },
  "bookables": [
    { "id": "bk_table_2", "label": "Стол 2", "capacity": 4, "selection": "single" }
  ],
  "occasion": {
    "id": "occ_tonight_1900",
    "kind": "slot",
    "starts_at": "2026-09-16T19:00:00+05:00"
  },
  "inventory": [
    { "bookable_id": "bk_table_2", "state": "held" }
  ]
}
```

| Поле | Кто пишет | Кто читает |
|------|-----------|------------|
| `plan.nodes` | Редактор на **сайте** | Мобилка + веб (только view) |
| `bookables` | Хозяин (список / привязка к фигуре) | Все |
| `inventory[].state` | Бэк по запросам/броням | Клиент красит фигуру |
| `role: decor` | Хозяин | Не кликается |
| `role: bookable` | Хозяин | Клик → запрос, если `free` |

Координаты на холсте — **абсолютные px** в `canvas.width/height` (нормализуем на клиенте в доли экрана).  
Кино = те же `nodes` + кресла `selection: multi`. Билеты без схемы = только `bookables`, без `plan`.

## Определения (не «место и время»)

В продукте и в коде — эти слова. «Место» / «время» в UI только как пояснение, не как сущности.

| Термин | EN-ключ | Определение |
|--------|---------|-------------|
| **Объект брони** | `bookable` | То, что гость **выбирает купить / занять**: билет-тариф, стол, кресло, зона. Свой `id`, подпись (свободный текст хозяина), `capacity`, цена-ориентир, `kind`: `ticket` \| `seat` \| `zone`. Живёт в каталоге; на схеме может быть привязан к фигуре (`plan_node_id`). |
| **Повод / occasion** | `occasion` | Конкретный **момент визита**, на который считается занятость. Два вида: **сеанс** (`session`) — одно время начала (кино, концерт); **слот** (`slot`) — окно «с–до» (ресторан). Не рисуется на плане. |
| **Занятость** | `inventory` | Состояние **пары** `bookable` + `occasion`: `free` \| `held` \| `taken`. Один стол свободен в одном слоте и занят в другом — это норма. |
| **Запрос** | `reservation` | Заявка гостя: выбранные bookable(ы) + occasion → `requested` → решение хозяина. |
| **Заведение** | `venue` | Точка хозяина: название, локация, TZ, режим сеанс/слот. |
| **План / фигура** | `plan` / `node` | Геометрия в ресурсе `space_plan` (Ресурсы). Фигура с `role: bookable` на витрине Брони ссылается на `bookable_id` **каталога заведения** (не хранить каталог внутри JSON ресурса). Декор — не кликается. |

**Формула:**

```
reservation = bookable(s) + occasion
inventory[bookable, occasion] ∈ { free, held, taken }
```

| Не говорить | Говорить |
|-------------|----------|
| «время» как сущность | **occasion** / сеанс / слот |
| «место» как всё подряд | **bookable** (или билет / стол / зона по `kind`) |
| «занято навсегда на схеме» | **inventory** на выбранный occasion |

### Сущности (кратко)

| Сущность | Смысл |
|----------|--------|
| **Заведение** | Точка: название, локация, TZ, режим (слот / сеанс) |
| **Bookable** | Объект брони (каталог A/B + опц. привязка к фигуре C) |
| **Occasion** | Сеанс или слот |
| **Inventory** | Занятость bookable на occasion |
| **Этаж / план / фигура** | Холст и геометрия (только сайт) |
| **Reservation** | Запрос: `requested` → решение admin |
| **Гостевая бронь / служебный блок** | Admin вручную, чтобы схема = реальность |

## Запрос → admin (не автомат)

Пока нет эквайринга: **человек решает**, система только держит место.

```
requested  →  confirmed  →  arrived  →  completed
     │              │            └──────→  no_show     (только admin)
     │              └───────────────────→  cancelled
     ├──────────────────────────────────→  declined
     ├──────────────────────────────────→  cancelled
     └──────────────────────────────────→  expired     (TTL soft-hold, не «одобрение»)
```

| Шаг | Что |
|-----|-----|
| Клиент выбрал объекты + время | Комментарий, число гостей → `requested` + soft-hold |
| TTL без ответа | Дефолт **45 мин** → `expired`, место свободно |
| Admin | Подтвердить / отклонить / «нужна доплата» + чат / написать |
| Доплата | Текст условия; деньги **вне** Clover; потом admin confirm вручную |
| Явка | Только admin: пришли / не пришёл |

Цена на объекте — **ориентир**. Итог — на усмотрение хозяина вне приложения.

**Отличие от записи:** там сразу `confirmed`; здесь сначала запрос — место/условия часто надо согласовать.

## Inbox хозяина

Вкладки: **Запросы** · **Подтверждённые** · **Сегодня** · **Архив**.  
Быстрые действия: подтвердить · отклонить · доплата · написать · пришли · завершена · не пришёл · отменить.  
Плюс: гостевая бронь, служебный блок.

Отдельный inbox от записи.

## Сценарии

### 1. Простые билеты (без рисунка)

1. Тег `venue`, заведение «Вечер поэзии».  
2. Тарифы: вход / VIP. Сеанс 20:00.  
3. Клиент: список → запрос → admin confirm.

### 2. Ресторан со схемой (стартовый вертикаль с холстом)

1. На **сайте** рисует зал и столы (`capacity`).  
2. Мобилка/веб: клиент кликает стол → запрос «нас 4».  
3. Soft-hold → admin → в день визита: пришли / no-show.  
**Мультивыбор столов v1:** один стол = один запрос.

### 3. Кино / театр

1. Рисует кресла (сетка-помощь — V2). Сеанс «Фильм · 19:00».  
2. Клиент: несколько кресел = один запрос.  
3. Тот же inbox.

### 4. Телефон / walk-in

Admin → гостевая бронь → на схеме сразу **занято**.

| Тема | Решение |
|------|---------|
| Имя | UI **«Бронь»**, тег **`venue`** |
| Лестница | A билеты → B список → C схема; можно расти без смены сервиса |

| Подтверждение | Только admin |
| Оплата | Вне скоупа v1 |
| Discovery | Не маркетплейс |

## Правила v1

- Рисует и публикует хозяин; Clover не модерирует «красоту».  
- Клиент видит только опубликованный план.  
- Клиент создаёт только **запрос**.  
- Нет общего inbox с записью.  
- Нет прайса мест на шапке профиля.
