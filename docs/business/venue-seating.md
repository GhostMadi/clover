# Бронь мест (схема зала)

**Статус:** черновик плана (продукт) — решения v1 зафиксированы  
**Для кого:** продукт / бизнес / дизайн  
**Не про:** SQL, RPC, canvas-код, имена файлов  

**Не путать с:** [booking.md](booking.md) — это **онлайн-запись на услугу** (время + мастер).  
Здесь — хозяин рисует пространство и помечает **что угодно** как объект брони; клиент шлёт **запрос**, admin решает вручную.

Связано: [profile.md](profile.md) · [settings.md](settings.md) · [chats.md](chats.md) · [notifications.md](notifications.md) · [publications.md](publications.md) · [features-catalog.md](features-catalog.md) · запись: [booking.md](booking.md)

---

## Зачем

Дать заведениям (кино, ресторан, театр и не только) **свою визуальную схему**: стены, двери, столы, кресла, зоны, этажи, цвета — как хозяин хочет.

Бронировать можно **не только «кресло»**: любая нарисованная фигура (или группа), которую хозяин пометил как **доступна к брони** — стол, ряд, кабинка, сцена-зона, парковка на плане и т.д. Смысл задаёт хозяин подписью и свойствами, не тип «только seat».

**Оплаты в Clover пока нет.** Клиент **не** получает бронь «сама собой»: он шлёт **запрос на бронь**. Дальше решает **только admin** (подтвердить, отказать, попросить доплату/залог вне приложения и т.д.). Система **не** подтверждает и **не** закрывает визит за человека.

Пока нет эквайринга, ценность = **хорошая операционка**: запросы, soft-hold, inbox, доплата-заметка, чат, гостевая бронь admin’ом, легенда на схеме — без кассы и без CRM.

Клиенту бронь показывается **в двух видах** (см. ниже):
1. **Визуально** — если у заведения/этажа есть опубликованная схема.  
2. **Списком** — всегда доступный способ выбора тех же объектов брони.

Полная кастомная отделка схемы — цель; в v1 ограничиваем инструмент рисования, но не навязываем шаблоны «только кино / только кафе».

## Два вида показа брони (продуктовое правило)

| Вид | Когда | Что видит клиент |
|-----|--------|------------------|
| **1. Визуальный** | Есть опубликованный план (схема этажа) | Холст: декор + кликабельные объекты; **легенда из 3 состояний** (см. ниже) |
| **2. Список** | Всегда (даже если схемы нет) | Тот же каталог строками; **свободные сверху**; видно «ожидает ответа» |

Хозяин настраивает витрину:

| Настройка | Поведение |
|-----------|-----------|
| Только список | Схемы нет или скрыта; клиент только списком |
| Визуал + список | Есть схема → по умолчанию визуал, переключатель «Список» |
| Только визуал | Только схема (если схемы нет — fallback на список, чтобы бронь не ломалась) |

**Правило:** объект брони один и тот же в обоих видах (тот же id). Список и схема не два разных каталога.

### Легенда состояний объекта (схема и список)

| Состояние | Смысл | Клиент |
|-----------|--------|--------|
| **Свободно** | Можно запросить | Кликабельно |
| **На рассмотрении** | Soft-hold чужого или своего `requested` | Нельзя взять другому; своему — «ожидает ответа» |
| **Занято** | `confirmed` / служебный блок / гостевая бронь admin | Недоступно |

## Отличие от «Онлайн-записи»

| | Онлайн-запись [booking.md](booking.md) | Бронь по схеме (этот док) |
|--|----------------------------------------|---------------------------|
| Объект | Услуга + слот + мастер | **Любой** помеченный объект на плане (+ время/сеанс) |
| Создание | Сразу `confirmed` | Сначала **`requested`** (запрос) |
| Витрина | Каталог услуг | Схема **и/или** список объектов брони |
| Типичный бизнес | Салон, консультация | Кино, ресторан, театр, зал, своя раскладка |
| Тег / вход | `booking` | Отдельный тег **`venue`** (UI: «Бронь мест») — **не** смешивать с записью |
| Inbox | Свой у записи | **Свой** у брони мест — общего inbox нет |

Один аккаунт может иметь **и** запись, **и** эту бронь — разные сервисы.

## Участники / роли

| Роль | Кто | Делает |
|------|-----|--------|
| **Хозяин (host / admin)** | Профиль с тегом `venue` | Заведение, схема, bookable, сеансы/слоты, витрина, inbox, гостевые брони, служебные блоки |
| **Клиент** | Авторизованный, **не** хозяин этого заведения | Запрос с профиля / поста / карты / диплинка; комментарий + число гостей; отмена по правилам; чат |
| **Гость (незалогинен)** | Не в скоупе v1 для запроса | Публичный просмотр — позже |

Нет отдельного «бизнес-аккаунта» — обычный профиль + тег сервиса (как `booking`).

## Discovery (как у записи — без маркетплейса)

Discovery **не** цель SEO/каталога залов. Входы:

| Вход | Поведение |
|------|-----------|
| **Тег `venue` на профиле** | У гостя кнопка **«Забронировать место»**; на шапке **нет** прайса и списка мест |
| **Пост → CTA** | Как услуга у записи: при создании поста хозяин с тегом `venue` привязывает **заведение** (опц. сеанс) → гость бронирует с поста. Подробно ниже |
| **Карта / локация** | Точка заведения на карте → та же витрина |
| **Диплинк** | Прямая ссылка на заведение / сеанс |

**Самобронь запрещена:** у своего заведения / на своём посте кнопки запроса нет.

## Заведение / сеанс на посте (как услуга записи)

Тот же паттерн, что **услуга ↔ пост** в [booking.md](booking.md) и [publications.md](publications.md).

Если у автора тег **`venue`** и есть хотя бы одно заведение, при **создании** публикации можно привязать:

| Привязка | Обязательность | Смысл |
|----------|----------------|--------|
| **Заведение** | Да, если включили блок «бронь с поста» | Куда ведёт CTA |
| **Сеанс** | Опционально | Кино/театр: сразу этот сеанс; без сеанса — витрина заведения (выбор слота/сеанса) |

**На посте у гостя:**

| Кто | Что видит |
|-----|-----------|
| Гость | Блок заведения (название, опц. сеанс) + **«Забронировать место»** — тот же client flow, заведение (и сеанс, если был) уже выбраны → схема/список → **запрос** |
| Автор своего поста | Превью привязки **без** кнопки брони — к себе нельзя |
| Заведение снято / не опубликовано / нет bookable | CTA нет, пост остаётся |

**Правила (как у услуги записи):**

- Привязка **только при создании** поста. Сменить заведение/сеанс после публикации отдельным экраном **не делаем** (пост = снимок витрины; другое заведение → новый пост).  
- Неактивное / удалённое заведение → CTA пропадает само.  
- Один пост → **одно** заведение (0..1). Сеанс — 0..1 внутри этого заведения.  
- Пост может одновременно иметь услугу записи **и** бронь мест (два разных CTA), если у автора оба тега — редкий случай, не запрещаем.  
- Flow с поста **не** auto-confirm: дальше обычный **запрос** → admin.

**Сценарий:** пост «Столик у окна · пятница» → гость тап «Забронировать место» → схема/список этого заведения (слот уже подсказан, если передали) → запрос с комментарием и числом гостей.

## Сущности

| Сущность | Смысл |
|----------|--------|
| **Заведение (venue)** | Точка: название, адрес/локация (опц.), часовой пояс, режим времени (слот / сеанс) |
| **Этаж / план (floor / layout)** | Один холст; у заведения несколько этажей. Переключатель у клиента — **только если этажей > 1** |
| **Фигура (shape)** | Элемент на холсте: стена, дверь, декор, стол, кресло, зона… |
| **Объект брони (bookable)** | Флаг bookable + подпись + опц. цена-ориентир + **`capacity`** (вместимость). Цена **не** списывается |
| **Сеанс / слот** | Session-based (кино) или slot-based (ресторан дата/время) |
| **Запрос / бронь (reservation)** | Клиент или admin + объект(ы) + время + статус + опц. комментарий + число гостей |
| **Служебный блок** | Admin помечает объект занятым на слот/сеанс **без** клиента (VIP, ремонт) |
| **Гостевая бронь** | Admin создаёт бронь «по телефону / walk-in» от имени гостя (без аккаунта или с привязкой профиля) — чтобы схема = реальность |
| **Режим витрины** | Визуал / список / оба |

## Запрос → admin (не автомат)

**Правило продукта:** за человека в Clover **ничего не решается само** — ни подтверждение брони, ни «оплата прошла», ни «визит состоялся», ни no-show.

Пока эквайринга нет, продукт = **заявки + ручное ведение**, не касса и не auto-booking.

| Шаг | Кто | Что происходит |
|-----|-----|----------------|
| Клиент выбрал объект(ы) + время | Клиент | Форма запроса: **комментарий** (опц.), **число гостей** (с учётом `capacity`). Создаётся **`requested`**. Soft-hold места |
| Soft-hold TTL | Система | Если admin **не ответил** за N мин (дефолт **45**, настройка хозяина) → статус **`expired`**, hold снимается. Это **не** отказ человека и **не** одобрение — только освобождение места + уведомление обеим сторонам |
| Admin смотрит inbox | Admin | Быстрые действия: **Подтвердить** / **Отклонить** / **Нужна доплата** / **Написать** (чат) |
| «Нужна доплата» | Admin | Флаг/шаг + короткий комментарий («депозит 5 000 ₸») + чат. Деньги **вне** Clover. Admin **вручную** потом подтверждает или отклоняет |
| Клиент отменяет | Клиент | По правилу окна → `cancelled`, hold снимается |
| Admin отменяет / отклоняет | Admin | `cancelled` / `declined` |
| Явка | Admin | Только вручную: **пришли** → **завершена** или **не пришёл** (`no_show`). Cron **не** ставит эти статусы |

**Статусы v1:**

```
requested  →  confirmed  →  arrived  →  completed
     │              │            └──────→  no_show     (только admin вручную)
     │              └───────────────────→  cancelled
     ├──────────────────────────────────→  declined    (только admin)
     ├──────────────────────────────────→  cancelled   (клиент или admin)
     └──────────────────────────────────→  expired     (TTL soft-hold; не «решение за хозяина»)
```

Доп. флаг на `requested` / `confirmed`: **`needs_surcharge`** (нужна доплата) + текст условия — пока admin не снимет / не подтвердит.

- Нет `pending_payment` / `paid` как автомата оплаты.  
- **Запрещено:** auto-confirm; auto-complete; auto no-show «за хозяина»; система «одобрила за хозяина».  
- **`expired`** — единственный системный переход: снятие hold по TTL, не решение о визите.

Цена на объекте — **ориентир** на витрине. Итоговая сумма / доплата — на усмотрение admin вне приложения.

**Отличие от онлайн-записи:** в [booking.md](booking.md) запись сразу `confirmed`. Здесь — **сначала запрос**, потому что место/стол/условия часто нужно согласовать с человеком.

## Главная идея хозяина: свобода рисования

Хозяин **не** обязан брать готовый шаблон «кино 10×12». Он может:

1. Создать заведение и этаж.  
2. **Рисовать** на холсте: стены, двери, проходы, столы, кресла, сцену, бар — как хочет.  
3. Красить, слоить, подписывать.  
4. Пометить **любые** фигуры / группы как **объекты брони** (+ `capacity`, цена-ориентир).  
5. Включить показ: **визуал** и/или **список**.

**Этажи** — отдельные планы. У клиента переключатель этажей — только если их больше одного.

Редактор: **веб-first** (тяжёлый холст). Клиентский выбор мест — **мобилка + веб**.

## Сценарии

### 1. Ресторан: стол на дату/время (**стартовый вертикаль v1**)

1. Хозяин: тег `venue`, заведение «Кафе N», рисует зал и столы (`capacity` 2–6).  
2. Витрина: визуал + список.  
3. Клиент: стол + дата/время + «нас 4» + комментарий → `requested`.  
4. Soft-hold; admin подтверждает или просит депозит вне Clover → вручную confirm.  
5. В день визита admin: пришли → завершена **или** не пришёл.

**Мультивыбор в ресторане v1:** один стол = один запрос.

### 2. Кино / театр: ряды и сеанс (второй режим / V1c-bis)

1. Хозяин рисует кресла (сетка рядов — **помощь** редактора в V2, не обязательство).  
2. Сеанс «Фильм · 19:00».  
3. Клиент: **несколько кресел** = один запрос (мультивыбор).  
4. Дальше тот же inbox / без автомата.

### 3. Admin закрыл стол по телефону

1. Звонок: «стол у окна на 20:00».  
2. Admin → **гостевая бронь** на этот объект/слот → на схеме сразу **занято**.  
3. Схема не расходится с залом.

### 4. Два вида показа

1. Опубликованная схема + оба режима витрины.  
2. Клиент: схема по умолчанию; переключатель «Список».  
3. Без схемы — только список; запрос всё равно возможен.

## Стыки → решения (v1) — закрыто

| Тема | Решение |
|------|---------|
| Первый вертикаль | **Ресторан (slot-based)** первым; кино (session) — следом на той же модели |
| Редактор | **Веб-first**; клиент — веб + мобилка |
| Имя / тег | UI **«Бронь мест»**, тег профиля **`venue`** |
| Свобода рисования | Набор фигур + цвет/поворот/слой; не Illustrator |
| Что бронируется | Любая bookable-фигура; декор не кликается |
| Витрина | Визуал и/или список; один каталог; легенда 3 состояний |
| Ресторан vs кино | Ресторан: **1 стол / запрос**; кино: **мультивыбор** кресел в одном запросе |
| Capacity / гости | На объекте `capacity`; в запросе число гостей (не больше capacity, warn если больше) |
| Комментарий клиента | Поле в запросе v1 |
| Soft-hold + TTL | Пока `requested`; дефолт **45 мин** → `expired` + уведомление (не decline) |
| Подтверждение | Только admin; клиент → `requested` |
| Доплата | Флаг `needs_surcharge` + текст + чат; деньги вне Clover |
| No-show | Только кнопка admin; без cron |
| Гостевая бронь / блок | Admin v1 |
| Inbox | Вкладки + быстрые действия |
| Discovery | Тег, **пост↔заведение (как услуга↔пост)**, карта, диплинк; **не** маркетплейс |
| Пост ↔ бронь | При создании: 0..1 заведение (+ опц. сеанс); CTA «Забронировать место»; смена после публикации — нет |
| Самобронь | Запрет |
| Версия схемы | Новая версия плана; snapshot на брони |
| Связь с записью | Разные сервисы, разные inbox |
| Оплата / эквайринг | Вне скоупа; бонусы на места — V2 |
| Цена на объекте | Ориентир на витрине — да |

## Правила / ограничения (v1)

- Хозяин рисует и публикует схему сам; Clover не модерирует «красоту».  
- Клиент видит только **опубликованный** план.  
- Свободно / на рассмотрении / занято — три состояния; hold и занятые недоступны другим.  
- Клиент создаёт только **запрос**; решения по броням — **только admin вручную** (кроме TTL → `expired`).  
- Отмена клиентом — по правилу окна (`requested` / `confirmed`).  
- Этажей — разумный лимит (число при бэке).  
- Нет общего inbox с онлайн-записью.  
- Нет прайса мест на шапке профиля.

## Вне скоупа (v1)

- **Оплата / эквайринг / холд карты / чеки / статусы paid**  
- Электронные билеты с QR как у Ticketon  
- AR / 3D / CAD / DWG  
- Live POS официанта  
- Динамическое ценообразование AI  
- Совместное редактирование схемы realtime  
- Смешение UI / inbox с онлайн-записью  
- Маркетплейс заведений / SEO-каталог  
- Auto-approve / AI «умный зал»  
- Бонусы за бронь мест (→ V2)

3. Длительность слота ресторана по умолчанию (90 / 120 мин)?

## Коротко одной схемой

```
Тег venue → схема (веб) → bookable → слот/сеанс
Клиент (профиль/пост/карта): запрос + гости + комментарий → requested + soft-hold
                    TTL без ответа → expired (не «одобрение»)
Admin inbox: confirm / decline / доплата+чат / гостевая / блок
         confirmed → arrived → completed | no_show (всё вручную)
Без эквайринга; без автомата за человека; без маркетплейса
```
