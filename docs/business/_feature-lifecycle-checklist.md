# Чеклист: фича как жизненный цикл

**Зачем:** пройти одни и те же этапы, чтобы фича могла **жить сама** (роли → вход → действие → учёт → выход / архив), без дыр «доделаем потом» в логике.  
**Ориентир:** как собирали [attendance.md](attendance.md).  
**Не про:** имена Dart-файлов, SQL в этом файле — только порядок мысли.

Связано: [_template.md](_template.md) · [features-catalog.md](features-catalog.md) · правила `clover-feature-discipline` / `clover-harmony` / `clover-business-process`

---

## Порядок (не перескакивать)

```
1. Смысл и границы
2. Роли и сущности
3. Жизненный цикл (happy path)
4. Карта экранов
5. Стыки и споры → решения
6. Сеть / sync / сессии (если есть данные)
7. Уведомления и каналы
8. Вне скоупа
9. Mock UI по процессу
10. Дожим UX + статус в каталоге
11. Бэк по контракту (отдельно, после процесса)
```

Код и Supabase — **после** пунктов 1–8 (хотя бы черновик 1–8). Mock UI (9) можно параллельно уточнять процесс, но не вместо него.

## Чекеры по этапам

### 1. Смысл и границы

- [ ] Одно предложение: **зачем** фича пользователю  
- [ ] Чем **не** является (анти-CRM, анти-дубль соседней фичи)  
- [ ] Связь с существующими процессами (ссылки, не копипаста)

### 2. Роли и сущности

- [ ] Кто участник (роли) и что каждая делает  
- [ ] Сущности: что создаётся, что «живёт», что архивируется  
- [ ] Один аккаунт может быть в **нескольких ролях**? Как не смешивать UI

### 3. Жизненный цикл (главный чекер)

Фича «стоит сама», если для объекта есть полный круг:

| Фаза | Вопрос | Пример (посещаемость) |
|------|--------|------------------------|
| **Создать** | Как появляется сущность? | Компания + чат |
| **Пригласить / подключить** | Как человек входит в контур? | Invite в чат → Accept |
| **Активировать** | Когда можно действовать? | Membership + ack правил |
| **Действовать** | Главное ежедневное действие | Punch |
| **Учитывать** | Где правда часов / статуса | Аналитика, ЗП, отсутствия |
| **Исключить** | Как выйти без потери истории? | Архив → повторный invite |
| **Отклонить / игнор** | Что если не принял? | Reject → вне команды |

- [ ] Таблица фаз заполнена **для главной сущности**  
- [ ] Нет тупика: «создали, а вернуть/выгнать нельзя»  
- [ ] Нет скрытого второго способа обойти цикл (напр. «сразу активный» без Accept)

### 4. Карта экранов

- [ ] Admin / worker (или свои роли) — дерево экранов  
- [ ] Откуда вход в фичу (Настройки / Профиль / Chat / …)  
- [ ] Кто **не** видит фичу → **0** лишней работы (запросов / badge)

### 5. Стыки и споры → явные решения

Пройти пары, которые обычно ругаются:

- [ ] Статус A vs статус B (напр. отсутствие vs пропуск)  
- [ ] Авто vs ручное утверждение (напр. переработка)  
- [ ] Блок vs инфо (напр. дежурный)  
- [ ] Архив / возврат  

Формат фиксации:

| Тема | Решение (одна строка) |
|------|------------------------|
| … | … |

- [ ] Нет двух противоречащих правил в разных местах дока  
- [ ] После спора — **одно** решение, не «оба варианта пока»

### 6. Сеть / sync / сессии (если есть данные на устройстве)

- [ ] Что можно **offline**, что **только online**  
- [ ] Outbox / retry / без дублей (`client_id`)  
- [ ] Кто источник правды (сервер vs кэш)  
- [ ] Logout / смена аккаунта → wipe  
- [ ] Несколько устройств: см. [authentication.md](authentication.md) (mobile vs web), плюс конфликты записи этой фичи

### 7. Уведомления и каналы

- [ ] Что идёт в **чат-карточку**, что в in-app, что в push (v2)  
- [ ] Критичные действия (invite, правила, approve) — канал назван  
- [ ] Mock: хотя бы UI карточки / sheet, если канал — часть UX

### 8. Вне скоупа

- [ ] Явный список «не в v1» (чтобы не расползтись)  
- [ ] Отличие от соседней фичи (таблица, если легко перепутать)

### 9. Mock UI по процессу

- [ ] Экраны закрывают фазы цикла (не только «красивый хаб»)  
- [ ] Спорные решения видны в UI (не только в тексте дока)  
- [ ] Каталог / хаб «все экраны» — опционально для ревью

### 10. Дожим и учёт

- [ ] 2–3 UX-дыры из ревью закрыты или в «позже» с причиной  
- [ ] Строка в [features-catalog.md](features-catalog.md) (🟢🟡🔴)  
- [ ] Короткая схема «одной картинкой» в конце дока процесса

### 11. Бэк (после процесса)

- [ ] Spec в `docs/supabase/` + миграции  
- [ ] RLS = права из процесса, не «спрятать кнопку»  
- [ ] Flutter-модель = контракт, не наоборот

## Мини-чекер «можно ли стоп?»

Перед «процесс готов»:

1. Новый человек по доку цикла понимает путь без кода?  
2. Все споры сведены к таблице решений?  
3. Offline/online и сессии не противоречат Auth?  
4. Вне скоупа не содержит обязательное для жизни цикла?  
5. Mock можно пройти руками end-to-end по happy path + reject/archive?

Если да ×5 → **бизнес-процесс COP** для этой фичи. Дальше — бэк / прод-полировка.
