## 1. Смысл и границы

**Зачем:** один раз нарисовать зал на сайте → переиспользовать как **ресурс** при создании заведения / точки Записи / (опц.) компании посещаемости. Гость бронирует **тем же объектом**, что и в списке — схема не второй каталог.

**Чем не является:**

| Не это | Почему |
|--------|--------|
| Отдельный сервис «Схемы» | Нет тега `space_plans`; это справочник Ресурсов, как locations |
| Каталог услуг / bookable | Услуги и места живут на сущности сервиса |
| CRM / касса / оплата | Заявки и запись — в своих сервисах |
| Учёт смен по клеткам | Посещаемость только опц. смотрит план |

**Связь:** Ресурсы = геометрия · сервис (Запись / Бронь) = bind + занятость · [entity-location-bind-plan.md](entity-location-bind-plan.md) = тот же паттерн, что `location_id`.

## 2. Роли и сущности

| Роль | Кто | Делает со схемой |
|------|-----|------------------|
| **Автор ресурса** | Владелец профиля + тег `resources` | Создаёт / правит / публикует / архивирует схемы **на сайте** |
| **Хозяин сервиса** | Тот же или другой контур с `booking` / `venue` / `attendance` | Привязывает **published** схему к точке / заведению / компании |
| **Гость** | Клиент записи / брони | Только смотрит published JSON + кликает bookable (логика клика — в сервисе) |
| **Не участник** | Без тега resources и без bind | **0** экранов схем в Ресурсах |

Один аккаунт может быть и автором схем, и хозяином Записи — UI не смешивает: Рисовалка = Ресурсы; ценники/bind = хаб точки / заведения.

| Сущность | Смысл | Архив |
|----------|--------|--------|
| **`space_plan`** | Геометрия: этажи + nodes (emoji bookable/decor, фигуры, text) | Не выбирается в новых create; старые bind остаются, пока не отвяжут |
| **Черновик / published** | Только published виден гостю и в селекторе bind | Draft правится на сайте без поломки витрины |
| **Ссылка `entity.space_plan_id`** | Точка / заведение / компания → одна схема | Отвязка / замена на сущности; удалить ресурс нельзя, пока есть ссылки |

## 3. Жизненный цикл ресурса

| Фаза | Как |
|------|-----|
| **Создать** | Ресурсы → Схемы → «Новая» (сайт). С мобилки — CTA «Открыть на сайте» / QR, без рисовалки |
| **Рисовать** | Только сайт: этажи, фигуры, emoji place/decor, связки `groupId`, AI/вставка JSON |
| **Опубликовать** | Draft → published (версия++); витрина и bind-селектор подхватывают |
| **Привязать** | Create/edit точки / заведения / компании → выбрать из **своих published** |
| **Действовать (гость)** | Смотрит JSON + inventory/bind сервиса — не пишет в ресурс |
| **Отвязать / заменить** | На сущности; иначе нельзя удалить схему |
| **Архив** | Не в новых create; уже привязанные продолжают читать published snapshot до замены |
| **Отклонить** | Невалидный JSON / пустой этаж → не применяется; publish с 0 bookable — можно (только декор / ориентация) |

Нет тупика «привязали и нельзя снять» — отвязка на сущности всегда доступна хозяину.

## 5. Стыки → решения

| Тема | Решение |
|------|---------|
| Ресурсы vs Запись vs Бронь | Схема = общий ресурс. Услуга/мастер = слой Записи. Bookable/inventory = слой Брони. Не один inbox |
| Ценник на фигуре rect | **Нет.** Для Записи прайс только на emoji `role: bookable` |
| Один id списка и схемы | Бронь: один `bookable_id`. Запись: bind `node_id` → `service_id` (+ staff); услуга не дублируется |
| Обязательна ли схема при create | **Нет.** Без схемы — только список / классическая запись |
| Удалить схему со ссылками | **Нельзя**, пока не отвяжешь (зеркало location) |
| Inventory на ресурсе | **Нет.** Занятость только на сущности сервиса |
| Запись: выбор места в v1 | **Да** (полный путь через emoji-bind) — см. [space-plan-emoji-pricing.md](space-plan-emoji-pricing.md). Старое «только просмотр» снято |
| Посещаемость + схема | Только **просмотр** плана объекта; punch по клеткам — вне скоупа |
| Рисовалка на телефоне | **Нет в v1** |
| Витрина хозяина (Бронь) | только список · схема+список · только схема; без схемы → fallback список |

## 6. Сеть / sync / сессии

| Что | Правило |
|-----|---------|
| Правда геометрии | Сервер `space_plans` (после SPEC); mock — localStorage / asset JSON |
| Правда bind / inventory | На сущности сервиса, не в JSON схемы |
| Offline | Гость: кэш последнего published JSON ок для просмотра; создать запись / заявку — **online** |
| Logout / смена аккаунта | Wipe локальных draft / mock bind ключей этого user |
| Несколько устройств | Publish с сайта → мобилка читает версию; конфликт draft — last-write на сайте |

## 7. Уведомления

| Событие | Канал v1 |
|---------|----------|
| Publish схемы | Нет push; витрина просто видит новую версию |
| Bind / отвязка на точке | Нет отдельного нотифа |
| Гостевая запись / заявка брони | Как в [booking.md](booking.md) / [venue-seating.md](venue-seating.md) — схема не меняет канал |

## 8. Вне скоупа (v1)

- Рисовалка в мобильном приложении  
- Схема как обязательное поле create  
- Inventory / цены внутри ресурса  
- Один inbox Запись+Бронь  
- CAD / DWG  
- Учёт смен по клеткам схемы  
- Публичный просмотр схемы без аккаунта

## 9. Слои данных (не смешивать)

| Слой | Где | Кто пишет |
|------|-----|-----------|
| Геометрия (`floors` / `nodes`) | Ресурс `space_plan` | Только веб-редактор |
| Адрес | `location` | Ресурсы |
| Каталог bookable / услуги | На сущности сервиса | Хозяин сервиса |
| Emoji → услуга (+ мастер) | На **точке Записи** | [space-plan-emoji-pricing.md](space-plan-emoji-pricing.md) |
| Inventory free/held/taken | Bookable × occasion (Бронь) | Бэк сервиса Бронь |

```
Ресурсы: space_plan (published)
    ↓ space_plan_id
Точка / заведение / компания
    ↓ свой слой
Гость: схема + действия сервиса
```

## 10. Bind при create (паттерн location)

| Поле | Обязательность |
|------|----------------|
| `location_id` | По плану bind — обязательно |
| `space_plan_id` | Опционально |

| Сервис | Сущность | Зачем схема |
|--------|----------|-------------|
| **Бронь** (`venue`) | Заведение | Визуальная бронь столов / мест |
| **Запись** (`booking`) | Точка | План салона + выбор места → услуга/мастер |
| **Посещаемость** | Компания | Опц. просмотр плана |

## 12. Очередь после процесса

1. Mock create entity — поле «Схема» рядом с адресом (если ещё дырка).  
2. SPEC: `space_plans` + `space_plan_id` на entities.  
3. RLS: автор ресурса пишет геометрию; хозяин сущности пишет только FK.  
4. Клиенты mobile/web на одном контракте.

## Коротко одной схемой

```
Ресурсы (сайт): нарисовать → Publish
        ↓ space_plan_id (опц.)
Запись / Бронь / Attendance: сущность
        ↓ свой bind / inventory
Гость: Список | Схема → действие сервиса
```
