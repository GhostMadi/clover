## Почему так (твоя логика)

В Clover **нет иерархий** «админ над работником». Нет отдельного типа аккаунта и нет скрытых ролей в продукте.

**Логика записи уже правильная** ([booking.md](booking.md)) — её не ломаем. Меняем **удобство входа** и **добавляем** экран для человека, которому другие дают заказы (просто так вышло, что он «как исполнитель» — не должность).

Есть **обычный профиль** и **теги**, которые человек сам включает в edit profile. Тег = **сила**: появляется кнопка / быстрый вход на нужный экран и открываются связанные запросы. Без тега — кнопки нет, лишние сценарии клиент не дергает.

Запись — первый сервис. Удобства раскладываем **тремя равными сценариями одного человека** (можно совмещать на одном аккаунте):

| Сценарий | Нужен тег? | Что открывается |
|----------|------------|-----------------|
| Принимаю запись к себе | **`booking`** | Быстрая кнопка → страница хозяина (inbox, услуги, расписание…) |
| Смотрю заказы, которые мне дают другие | **`bookingCalendar`** (рабочее имя) | Кнопка на профиле → список аккаунтов-источников + детали своих заказов |
| Иду как клиент к кому-то | **нет** | Уже есть вход на «мои записи, куда мне идти» |

Никто никому не «подчинён» в модели продукта: один человек может иметь `booking`, другой — `bookingCalendar`, третий — оба, четвёртый — ни одного (только клиентский вход).

---

## Три силы рядом

```
Один аккаунт Clover
├── тег booking
│     └── кнопка быстрого входа → страница приёма записи (как хозяин точки)
├── тег bookingCalendar
│     └── кнопка на профиле → страница «мне дают заказы»
│           ├── список аккаунтов, которые назначают мне визиты
│           └── детально свои заказы по каждому / общий календарь
└── без этих тегов
      └── клиентский вход: записи, куда мне идти («Мои бронирования»)
```

Связь staff у чужого хозяина (ник / имя) **остаётся данными записи** (кого клиент выбирает в слоте).  
Но **показ кнопки календаря работника** — не «ты в staff → магия», а **сам выбрал тег** `bookingCalendar`. Так же, как хозяин сам выбирает `booking`.

Данные заказов для `bookingCalendar` всё равно берутся из привязок staff (`profile_id`): тег открывает UI; пустой список, если никто ещё не привязал — нормально.

## Приглашение исполнителя с аккаунтом Clover (через чат)

**Решение:** человека с ником Clover **нельзя** сразу записать в staff с `profile_id`.  
Сначала **заявка в чат** → **Принять** / **Отклонить** → только после Accept появляется связанный исполнитель.

Паттерн как у посещаемости ([attendance.md](attendance.md)): согласие через чат-карточку, не «сразу активный» с кнопки хозяина.

### Зачем

- Нет сюрприза: «меня повесили на запись без спроса».
- Сила `bookingCalendar` и чужие заказы на экране — только после явного согласия.
- Один понятный канал (DM), без отдельного типа аккаунта.

### Правила

| Тема | Решение |
|------|---------|
| Кого зовём через чат | Только поиск по **аккаунту Clover** (ник / профиль) |
| Имя без аккаунта | По-прежнему можно добавить **только строкой имени** (нет кому слать заявку) — без `profile_id`, без календаря у «работника» |
| Сразу в staff с `profile_id` | **Запрещено** |
| Канал | **DM** от аккаунта хозяина (у кого тег `booking`) к приглашённому |
| Карточка | Заявка вида: «Стать исполнителем записи · {имя / @хозяина}» → **Принять** / **Отклонить** |
| Пока ждём | У хозяина статус **«Ожидает»**; к услугам / слотам как linked Clover-staff **не** цепляем |
| Accept | Создаётся / активируется `booking_staff` с `profile_id`; можно назначать на услуги |
| Reject / игнор | Связи нет; хозяин может отправить заявку снова |
| Отозвать заявку | Хозяин может отменить pending (карточка / список ожидания) |
| Снять после Accept | Хозяин убирает из staff (как сейчас deactivate); повтор — снова через invite |
| Тег `bookingCalendar` | **Не** выдаём автоматически: человек сам включает, если хочет экран календаря |

### Жизненный цикл

| Фаза | Как |
|------|-----|
| Создать заявку | Хозяин: Услуги / исполнители → найти @ник → «Пригласить» |
| Доставить | В DM карточка заявки |
| Ожидать | Pending у хозяина; у получателя — Accept / Reject (нужен интернет) |
| Активировать | Accept → linked staff |
| Действовать | Назначение на услуги, слоты; у исполнителя при желании — тег `bookingCalendar` |
| Отклонить | Reject → вне staff |
| Исключить | Хозяин деактивирует staff; история записей сохраняется |

### UI (ориентир)

| Где | Что |
|-----|-----|
| Хозяин: список исполнителей | Активные + блок **Ожидают** (pending invites) |
| Хозяин: поиск ника | Не «Добавить», а **«Пригласить»** |
| Получатель: чат | Карточка заявки |
| Получатель: после Accept | Может включить `bookingCalendar` в edit profile |

### Вне скоупа v1 invite

- Групповой чат «салона» (в отличие от attendance company chat) — достаточно DM  
- Автотег `bookingCalendar`  
- Заявка человеку без аккаунта Clover  

### Статус реализации

**Процесс + бэк + mobile + web invite** — готово (Accept/Reject в DM, pending у хозяина).

## 1. Тег `booking` — сила «принимаю запись»

### Зачем тег, а не тоггл в кэше

Сейчас быстрый ярлык «Запись» живёт через **локальный тоггл / prefs (кэш)**.  
Цель: **источник правды — тег на профиле (бэк)**, без отдельного клиентского кэша «показывать ли кнопку».

| Было | Станет |
|------|--------|
| Пользователь включает ярлык в настройках → prefs / localStorage | Пользователь ставит тег **`booking`** в edit profile → тег с профиля |
| Клиент сам помнит «ярлык вкл» | Клиент читает теги профиля → рисует кнопку |
| Разный кэш на устройствах / мобилке vs сайте | Один ответ бэка везде |

Настройки → Запись (хаб услуг / inbox) могут остаться доступны из меню настроек **если есть тег**; отдельный «тумблер ярлыка» уходит или становится зеркалом тега (предпочтительно — только тег).

### Сила тега

| Слой | Что даёт `booking` |
|------|---------------------|
| Визуал | Быстрая кнопка / ярлык сбоку → сразу на страницу приёма (inbox / хаб записи) |
| Визуал для гостя | На **чужом** профиле CTA «Записаться», если у хозяина есть тег |
| Функции | Услуги, мастера, расписание, inbox всех записей точки, аналитика, привязка услуги к посту |
| Без тега | Нет быстрой кнопки; нет CTA «Записаться» на витрине; хозяинские RPC клиент не зовёт «на всякий случай» |

### Паритет мобилка + сайт

Один и тот же смысл на обеих платформах:

- есть тег → есть быстрый вход на страницу хозяина;
- нет тега → нет этого входа;
- настройки записи / inbox / услуги — с тем же гейтом.

## 2. Тег `bookingCalendar` — сила «мне дают заказы»

Рабочее имя ключа: **`bookingCalendar`** (EN-ключ в каталоге; подпись на фронте позже, напр. «календарь заказов» / «мне записывают»).

### Зачем отдельный тег

Не смешивать с `booking`:  
`booking` = «я принимаю к **своему** аккаунту».  
`bookingCalendar` = «я хочу видеть заказы, которые **другие аккаунты** вешают на меня как на исполнителя».

Человек сам решает, нужен ли ему этот экран. Без тега — нет кнопки, даже если где-то в данных он указан staff (можно уточнить позже: пустой стейт vs скрыть до первого назначения — в v1 достаточно «тег → экран, список может быть пуст»).

### Сила тега

| Слой | Что даёт `bookingCalendar` |
|------|----------------------------|
| Визуал | Кнопка **где-то на профиле** (свой профиль) → страница календаря/заказов |
| Экран | Список **аккаунтов**, которые подают ему заказы (точки, где он в staff с `profile_id`) |
| Деталь | По выбранному аккаунту (или общим списком) — свои визиты: услуга, время, клиент, статус… |
| Функции | Только staff-scoped чтение (и позже действия, если решим); **не** чужие услуги/аналитика точки |
| Без тега | Нет этой кнопки; клиент не открывает staff-календарь |

### Откуда данные

1. Тег на своём профиле → показать кнопку.  
2. Запрос: «аккаунты-хозяева, где я linked staff» + «мои записи как исполнитель».  
3. Мастер только по **имени** (без Clover-аккаунта) этот тег не использует — ему некуда войти.

### Паритет мобилка + сайт

Сейчас такого экрана нет нигде → сразу проектировать **оба** клиента одинаково (маршрут, гейт по тегу, те же RPC).

---

## 3. Клиент без тега — «куда мне идти»

Отдельный тег **не нужен**: любой авторизованный пользователь может записываться к другим и смотреть свои записи.

| | Сейчас | План |
|--|--------|------|
| Мобилка | Есть вход (⋯ / настройки) → **Мои бронирования** | Оставить; не завязывать на `booking` / `bookingCalendar` |
| Сайт | Есть `/app/settings/booking/my` (часто через хаб записи) | Явный вход **без** обязательного тега `booking` (не прятать клиентский список за силой хозяина) |

Паритет: на сайте такая же заметная точка входа, как на мобилке (профиль ⋯ / меню), не только «зашёл в хаб хозяина → Мои бронирования».

## Карта кнопок (итог)

| Кнопка | Условие показа | Куда ведёт | Где на профиле |
|--------|----------------|------------|----------------|
| Быстрый вход «Запись» (хозяин) | свой тег **`booking`** | страница приёма / inbox | **Нижняя** линия (админ) |
| «Календарь заказов» | свой тег **`bookingCalendar`** | аккаунты-источники + свои заказы | **Верхняя** линия (работник) |
| «Мои бронирования» (клиент) | авторизован | записи, куда **мне** идти | **не** в линиях сервисов (⋯ / меню) |
| «Записаться» на чужом профиле | у **хозяина** тег `booking` | клиентский flow | чужой профиль |

Один человек может видеть обе линии — это не иерархия, а набор включённых сил + базовый клиентский вход.

### Визуал линий (обязательно при вёрстке)

Полный паттерн: [`docs/code/ui/profile-service-shortcuts.md`](../code/ui/profile-service-shortcuts.md).

```
Верхняя линия — работник   (bookingCalendar, …)
Нижняя линия  — админ      (booking, …)

В одной линии:
  1–2 кнопки → иконка + текст
  3+ кнопок  → только иконка
Пустая линия не рисуется. Мобилка = сайт.
```

Цель: сервисы не забивают страницу профиля текстом, когда сил станет много.

## Фазы (мобилка и сайт вместе)

### Фаза 0 — договориться о ключах
- Зафиксировать EN-ключи: `booking` (уже есть), `bookingCalendar` (новый в каталоге тегов).
- Подписи только на фронте ([localization-dictionaries.md](localization-dictionaries.md)).
- Строка в [tag-powers.md](tag-powers.md): две силы рядом, без ролей «над / под».

### Фаза 1 — `booking` без кэша ярлыка
- Убрать (или перестать опираться на) тоггл ярлыка в prefs / localStorage.
- Быстрая кнопка = наличие тега `booking` с профиля (бэк).
- Синхронно: Flutter + web cabinet rail / accessory.
- Гейт хозяинских экранов и запросов по тому же тегу.

### Фаза 2 — клиентский вход на паритете
- Проверить, что «Мои бронирования» на сайте доступны **без** тега `booking` (отдельная точка входа, как на мобилке).
- Не смешивать клиентский список с хабом хозяина в навигации.

### Фаза 3 — тег `bookingCalendar` + экран
- Каталог + enum + edit profile (выбор тега).
- Кнопка на своём профиле (мобилка + сайт).
- Экран: список аккаунтов-источников → детали заказов.
- Бэк: RPC/RLS «где я staff» + «мои визиты как исполнитель» (не весь inbox чужой точки).
- Пустой список, если привязок ещё нет — ок.

### Фаза 4 — удобства поверх (по желанию)
- Пуш «новая запись на меня» при `bookingCalendar`.
- Действия по визиту с экрана календаря (если понадобится) — отдельно, не в v1 обязательно.
- Фильтры / «сегодня» на экране хозяина (`booking`) — не блокер для фаз 1–3.

## Что сознательно не делаем

- Иерархия «админ управляет работником» как продуктовая роль.
- Автопоказ календаря только потому что тебя добавили в staff — **без** тега `bookingCalendar` кнопки нет (симметрия с `booking`).
- Один тег на оба сценария (`booking` ≠ календарь чужих заказов).
- Ярлык хозяина только в device cache.
- Функционал «только мобилка» или «только сайт» — **нет**, оба клиента.

## Коротко

```
Все равны. Силы = теги, которые сам выбрал.

booking           → нижняя линия профиля → страница ПРИЁМА записи (вместо тоггла/кэша)
bookingCalendar   → верхняя линия профиля → аккаунты, что дают заказы + детали своих
без тегов         → «Мои бронирования» в ⋯ (куда мне идти) — паритет сайта

Линии: ≤2 → иконка+текст; ≥3 → только иконка. Мобилка + сайт. Нет иерархий.
```
