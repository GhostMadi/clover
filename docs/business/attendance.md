# Посещаемость

**Статус:** продуктовый процесс (UI + бэк ядра 🟢 v1.5 workplace/membership/punch/absences/payroll preview/duty/OT)
**Для кого:** продукт / бизнес / дизайн  
**Не про:** SQL, RPC, cubit’ы, имена файлов Dart  

Связано: [settings.md](settings.md) · [chats.md](chats.md) · [navigation-bars.md](navigation-bars.md) · [locations.md](locations.md) · [booking.md](booking.md) (отдельный сервис) · [tag-powers.md](tag-powers.md) · **ТЗ тегов:** [attendance-tz.md](attendance-tz.md) · [features-catalog.md](features-catalog.md) · бэк: [SPEC_ATTENDANCE_SYSTEM.md](../supabase/SPEC_ATTENDANCE_SYSTEM.md)

---

## Зачем

Учёт смен сотрудников по **геозоне** (пришёл / ушёл + свои отметки), с понятным расчётом часов и влиянием на зарплату — **без** CRM-кассы, лица и live-трекинга.

Один аккаунт Clover может быть **и админом своих компаний, и работником** в чужих или своих.

---

## Главный принцип продукта: 0 лишних запросов

| Кто | Что видит в UI | Запросы attendance |
|-----|----------------|--------------------|
| Не участвует | Нет кнопок, нет sheet, нет badge «по attendance» | **0** |
| Worker (тег `attendanceWork` + membership) | Профиль → верхняя «Посещаемость» | Bootstrap **только** если локально есть membership / флаг участия |
| Membership без `attendanceWork` | Нет punch / нет worker-кнопки; у админа — **«Неактивен»** | Bootstrap по делу (админ смотрит команду) |
| Admin (тег `attendance`) | Настройки → Сервисы → Посещаемость + нижняя «Управление» | Только при входе в сервис / по событию (invite, punch, ack) |

**Теги:** `attendance` (admin) + `attendanceWork` (worker). Create company / punch — строго с тегом (фронт + бэк). Детали: [attendance-tz.md](attendance-tz.md).

**Правило:** UI всегда читает **локальный snapshot**. Сеть — редко и по делу.  
Не участник **никогда** не «пингует» attendance API «на всякий случай».

Подробнее — [Синхронизация и трафик](#синхронизация-и-трафик-продуктово) и [Ревью: запросы](#ревью-лишние-запросы-и-оптимизация).

## Участники и сущности

| Роль | Кто | Делает |
|------|-----|--------|
| **Admin** | Владелец компании + тег `attendance` | Компании, геозона, типы отметок, работники, дежурные, отсутствия, переработка, зарплата, табель, аналитика |
| **Worker** | Принял invite + тег `attendanceWork` | Отметки, свои детали, история; принимает правила в чате |

| Сущность | Смысл |
|----------|--------|
| **Компания (workplace)** | Точка учёта: название, геозона, типы отметок, работники, правила ЗП, дежурства |
| **Папка** | Группировка компаний только в UI admin |
| **Membership** | Связь аккаунта с компанией после accept invite |
| **Групповой чат компании** | Создаётся с компанией; invite, правила vN, служебные карточки |
| **Архив работника** | Не в сменах и ЗП; история сохранена; вернуть только через **повторный invite в чат** |

## Карта экранов (как собрано в mock)

### Admin

```
Настройки → Сервисы → Посещаемость → Хаб
  └── Компания
        ├── Компания
        │     · Настройки → Геозона | Типы отметок | Зарплата
        │     · Работники → табы: Активные | Ожидают | Архив
        ├── Смены и учёт
        │     · Дежурные (очередь по рабочим дням)
        │     · Отсутствия (выходной / отпуск / больничный)
        │     · Переработка (утвердить / отклонить)
        │     · Табель + экспорт CSV
        ├── Отчёты → Аналитика (команда + день + человек)
        ├── Связь → Чат компании
        └── Демо → симуляция обновления правил
```

**Работники → Архив → тап:** sheet  
1. **Просмотреть детально** (календарь / часы / ЗП без возврата в активные)  
2. **Пригласить повторно** → чат, карточка «Стать частью команды · {компания}» → статус снова «Ожидают»

**Активный → долгое нажатие:** в архив.

### Worker

```
Профиль → Посещаемость (авто после accept)
  └── Хаб компании
        · статус смены, мини-сводка (часы / смены / опоздания)
        · Отметиться → экран punch
        · Мои детали → полный разбор за месяц

Punch:
  · геозона / GPS / правила — почему нельзя (понятный текст)
  · Пришёл / Ушёл + свои отметки
  · отмена последней + комментарий (необяз.)
  · история отметок

Home / resume:
  · bottom sheet «Надо отметиться» — только из локального кэша + GPS
```

## Сценарии

### 1. Создание компании

1. Admin: Сервисы → Посещаемость → создать компанию (опционально в папку).  
2. Создаётся **групповой чат** «Посещаемость · {название}».  
3. Admin настраивает геозону, типы отметок, при необходимости — зарплату / дежурных.  
4. Добавляет работников (в т.ч. себя — тот же invite-flow).

### 2. Приглашение (всегда через чат)

1. Admin: Работники → добавить → выбор пользователя Clover.  
2. В **чат** уходит заявка от компании: **«Стать частью команды · {компания}»**.  
3. Получатель: **Принять** / **Отклонить** (нужен интернет).  
4. После **Принять:** membership на аккаунт → кнопка «Посещаемость» на профиле → участник чата компании.

Пока не принял → в admin: вкладка **Ожидают**; у человека кнопки посещаемости **нет**.

### 3. Отметка (punch)

1. Worker → Посещаемость → компания → Отметиться.  
2. GPS сравнивается с **геозоной из локального кэша** (для проверки зоны сеть не нужна).  
3. Online: одна отправка punch; UI сразу.  
4. Offline: очередь; «сохранено, уйдёт при сети».

Отмена последней: комментарий необязателен; отменённая строка остаётся в истории как отменённая.

### 4. Sheet «Надо отметиться»

Только если есть membership + локальный `pending_punch` + GPS (для прихода — в зоне).  
**Отдельный API не вызывается.**  
Действия: отметить / подробнее / позже (snooze).

Если не приняты правила vN — вместо punch-sheet баннер «примите правила» → чат.

### 5. Изменение правил (config version)

1. Admin меняет геозону / типы / … → версия vN.  
2. Карточка в чат компании.  
3. Worker: «Понятно, принимаю» **на аккаунт**.  
4. До ack — punch заблокирован.

Данные diff — **внутри сообщения чата**; отдельный GET config не обязателен.

### 6. Дежурные

Admin задаёт **очередь** работников + **рабочие дни** недели.  
Каждый рабочий день дежурит следующий в очереди.  
На punch worker: баннер «Сегодня дежурит …» (инфо).

### 7. Отсутствия

Admin: выходной / отпуск / больничный на период.  
Такие дни **не считаются пропуском** в зарплате.

### 8. Переработка

Часы переработки → статус **ожидает**.  
В зарплату попадают **только утверждённые** admin.  
Отклонённые — без доплаты.

### 9. Зарплата

Правила: опоздания / переработка / пропуски / неполный день + ставки.  
По работнику: оклад, строки списаний/доплат, «к выплате».  
Архивные и непринятые в расчёт **не входят**.

### 10. Аналитика и детали

- Admin: сводка команды, календарь, карточка человека.  
- Worker: «Мои детали» — часы, метрики, ЗП-превью, календарь, журнал дней, история отметок, отсутствия.

### 11. Табель

Список часов за период + **экспорт CSV** (Excel).  
PDF — после бэка / отдельный шаг.

### 12. Архив

Уволен / не нужен в активных → архив (история жива).  
Вернуть = **не тумблер**, а **повторный invite в чат**.

## Синхронизация и трафик (продуктово)

| Принцип | Смысл |
|---------|--------|
| UI ← **локальный snapshot** | Открытие профиля / хаба / punch не = запрос |
| Bootstrap редко | Login при пустом/устаревшем кэше, pull-to-refresh, после flush outbox |
| Revision / версия | Лёгкая проверка вместо полного bootstrap |
| Чат realtime | Invite / правила **патчат кэш** из карточки сообщения |
| Accept / ack / punch | Один контрактный вызов; ответ желательно со snapshot-патчем |
| Logout | Wipe attendance cache + outbox |
| Не участник | **0** attendance-запросов при Home / Chat / Profile |

### Когда сеть нужна

| Действие | Нужна сеть? |
|----------|-------------|
| Показать sheet «надо отметиться» | Нет (кэш + GPS) |
| Проверить геозону для punch UI | Нет (кэш) |
| Отправить punch / accept / ack | Да (или outbox) |
| Открыть аналитику за месяц | Желательно из кэша; догрузка периода — по запросу экрана, не фоном для всех |
| Экспорт табеля | Локально из уже загруженных данных периода; тяжёлый отчёт — отдельный endpoint по кнопке |

### Сеть / outbox (v1)

| Кейс | Решение |
|------|---------|
| Punch без сети | Разрешён при геозоне в кэше + GPS. → **outbox**, UI: «сохранено, уйдёт при сети». |
| Payroll / duty / base salary / geofence / punch types Save offline | Optimistic + **outbox**; snackbar «Сохранено локально, синхронизируется». |
| OT add / approve / reject offline | Optimistic + **outbox** (`client_request_id`). |
| Absences offline | Optimistic + **outbox**. |
| Accept / Reject invite offline | **Нельзя.** Нужен интернет. |
| Ack правил offline | **Нельзя.** Punch закрыт, пока сеть + ack. |
| Outbox fail | `pending` → авто-retry при hydrate / foreground + flush. Без дублей (`client_punch_id` / `client_request_id`). |
| Два «Пришёл» offline подряд | Второй локально отклоняется («смена уже открыта») или conflict до flush. |
| После flush | `refreshRemote`; побеждает сервер. |

### Sync с бэком (v1)

| Кейс | Решение |
|------|---------|
| Источник правды | **Сервер.** Клиент = кэш + outbox. |
| Конфликт punch (2 устройства) | Первая принятая сервером запись побеждает; вторая → conflict → «не принято, обновите». |
| Отмена punch | Событие на сервере (tombstone). Offline-отмена в outbox до flush. |
| Смена геозоны / типов | После unacked vN punch по старому кэшу **запрещён** (как уже в процессе). |
| Аналитика admin | Не live; обновление при открытии / pull. |

### Сессии: мобильный vs веб (продукт Auth)

Полное правило — в [authentication.md](authentication.md) (сессии). Для посещаемости важно:

| Клиент | Правило |
|--------|---------|
| **Мобильный (iOS/Android)** | На аккаунт — **одна** активная мобильная сессия. Новый вход с телефона **выкидывает** предыдущий мобильный. |
| **Веб** | **Можно** входить. Веб **не** выкидывает мобильный и не выкидывается мобильным входом. Несколько веб-сессий допустимы. |

Следствия для attendance:

- На одном телефоне после takeover — wipe старого кэша (как logout), bootstrap заново.  
- Punch с «старого» мобильного после выкидывания → сессия мертва, outbox не шлётся под чужим контекстом.  
- Admin на вебе + worker на телефоне (один аккаунт) — ок: веб смотрит управление и **read-only детали**, телефон отмечает.  
- **Веб:** admin + worker read-only; punch / GPS на сайт не переносим. План: [website-gap-plan.md](website-gap-plan.md#8d--посещаемость-на-вебе).  
- **Хвосты сайта** (что ещё не догнали относительно этого процесса): [website-attendance-gaps.md](website-attendance-gaps.md) — не дублирует сценарии, только трекер.  
- Два телефона с одним аккаунтом **нельзя** держать одновременно: второй вход гасит первый.

### Аккаунт на устройстве

| Кейс | Решение |
|------|---------|
| Logout | Wipe attendance snapshot + outbox для этого `userId`. |
| Login другого человека на том же телефоне | Чистый старт; чужой кэш не мелькает. |
| Admin + worker один аккаунт | Один snapshot; sheet «надо отметиться» только при worker membership. |
| Ключ кэша | Всегда `userId` (+ platform при необходимости). |

## Продуктовые решения v1

| Тема | Решение |
|------|---------|
| **Invite (новый и из архива)** | Всегда карточка **в чат** человеку. Пока не принял → **Ожидают**. После Accept → **Активные** + добавляется в **групповой чат компании**. Не «сразу активный» с кнопки admin. |
| **Отсутствие vs пропуск** | Оформленное отсутствие (выходной / отпуск / больничный) **всегда перекрывает** пропуск в аналитике и в ЗП. |
| **Переработка** | Никогда не автоматом из «Ушёл позже». Цепочка: подсказка / заявка → **ожидает** → admin утверждает → только тогда в ЗП. |
| **Дежурный** | По умолчанию **информация** на UI («сегодня дежурит …») + уведомление команде — punch **не** блокируется. Опция **`duty_only_punch`**: если включена admin’ом, punch только у дежурного на сегодня. |
| **Сессии mobile / web** | Мобильный — **одна** сессия на аккаунт (новый вход выкидывает старый телефон). Веб — **можно** входить параллельно, без выкидывания мобильного. См. [authentication.md](authentication.md). |
| **0 запросов** | Не участник (нет workplace admin и нет membership) — **не** дергаем bootstrap на Home после первой пустой проверки. Вход в сервис / invite card → hydrate снова. |
| **Logout** | Wipe in-memory snapshot + outbox этого userId (чужой кэш не мелькает). |
| **Отмена punch offline** | Разрешена через outbox (как punch). |
| **Два «Пришёл» offline** | Второй локально отклоняется («смена уже открыта»). |

### Invite подробнее

```
Admin «Добавить» / «Пригласить повторно»
        ↓
Чат человеку: «Стать частью команды · {компания}»
        ↓
Accept → membership + групповой чат компании + Профиль «Посещаемость»
Reject / игнор → вне команды (не в Ожидают); можно пригласить снова
```

### Переработка визуально (продукт)

```
Ушёл позже / часы сверх   →   НЕ деньги
        ↓
Подсказка «возможна переработка» или заявка
        ↓
Статус: Ожидает  →  Admin: Утвердить | Отклонить
        ↓
Утверждено → строка в ЗП    |    Отклонено → без доплаты
```

### Дежурный визуально (продукт)

```
Admin: Дежурные → очередь + рабочие дни → сохранить
        ↓
Уведомление команде (кто дежурит / смена очереди)
        ↓
На punch / хабе worker: баннер «Сегодня дежурит: …» (инфо)
На admin «сегодня»: бейдж у человека
        ↓
По умолчанию: отметка доступна всем принятым
Опция «Отметка только у дежурного»: punch только у on-duty на сегодня
```

Папки компаний — группировка только в admin-хабе (без влияния на punch).

## Ревью: где логика спорит / неудобно / оптимизировать

Ниже — просмотр собранных экранов **против** правил продукта и хотелки «бэк ↔ фронт без лишних запросов».

### A. Логика конфликтует или размыта

| Место | Проблема | Как должно быть |
|-------|----------|-----------------|
| **Архив → «Пригласить повторно»** | — | ✅ Invite в чат → Ожидают → Accept → Активные + чат компании |
| **Зарплата vs отсутствия** | — | ✅ Оформленное отсутствие перекрывает пропуск |
| **Переработка vs punch** | — | ✅ Подсказка → заявка → approve → ЗП (UI pipeline) |
| **Дежурный** | — | ✅ Инфо-баннер + уведомление; опция `duty_only_punch` — жёсткий gate |
| **Отмена отметки** | Worker отменяет локально; admin в аналитике может ещё видеть старое до sync | Отмена = событие на сервере (или tombstone); reconcile на всех устройствах |
| **Admin + Worker в одном аккаунте** | Два входа (Настройки vs Профиль) — ок, но sheet «надо отметиться» не должен мешать admin-хабу | Sheet только для membership-роли worker; ярлык admin ведёт в управление |
| **Типы отметок «ожидается в»** | Scheduled time выглядит как жёсткий слот | Продуктово: это **ожидание** для опоздания, не запрет punch вне времени (если не решим иначе) |

### B. Неудобно пользователю

| Место | Почему больно | Дожим |
|-------|---------------|--------|
| Нет экрана **«Сегодня на смене»** у admin | — | ✅ Блок «Сегодня» сверху компании |
| Нет **запроса на исправление** | Worker ошибся GPS / забыл «Ушёл» — только отмена или звонок | ✅ Worker → запрос → admin approve |
| Worker не видит **дежурного** на punch | Очередь настроена, но в день смены не подсвечена | Строка «Сегодня дежурит: …» на punch / хабе |
| **Долгое нажатие → архив** | — | ✅ + явная «В архив» в sheet активного |
| Invite / правила **только текстом** в mock | — | ✅ Карточки в mock-чате компании |
| Табель CSV «путь в буфер» | Для бизнесмена странно | Share sheet / «Открыть файл» после бэка |
| Много экранов компании подряд | Уже разбили секциями — ок; дальше не раздувать хаб без нужды | Новые вещи — внутрь существующих секций |

### C. Оптимизация запросов (главная хотелка)

**Цель:** фронт и бэк дружат; пользователь **не платит** запросами за экраны, которые ему не нужны.

| Правило | Делать | Не делать |
|---------|--------|-----------|
| Участие | Один флаг / membership list в prefs после login или chat-события | На каждом cold start дергать `/attendance/me` у всех юзеров приложения |
| Экраны | Читать snapshot; сеть — refresh / действие | При каждом открытии «Работники» / «Зарплата» / «Мои детали» полный reload |
| Punch | Геозону из кэша; 1 write на punch | Перед каждой кнопкой «Пришёл» GET геозоны с сервера |
| Pending sheet | Только локально | Polling «нужно ли отметиться?» |
| Аналитика | Кэш периода; догрузка при смене месяца / pull | Фоновый prefetch всех работников на login |
| Экспорт | Из уже загруженного периода или один export-RPC по кнопке | Генерация отчёта при открытии табеля |
| Chat-карточки | Патч snapshot из payload сообщения | После каждого сообщения чата full attendance bootstrap |
| Admin vs Worker | Admin-данные (ЗП команды, approve OT) только на admin-экранах | Worker-хаб не тянет payroll всей команды |

**Контракт «один экран ≈ один осмысленный запрос»** (когда сеть всё же нужна):

| Экран / действие | Запрос |
|------------------|--------|
| Bootstrap участника | 1× snapshot (или revision → snapshot if changed) |
| Accept invite / ack rules | 1× RPC → patch |
| Punch / cancel punch | 1× write |
| Список работников (refresh) | 1× list + counts по вкладкам |
| Аналитика периода | 1× overview (+ worker detail по id при открытии карточки) |
| Зарплата (preview) | 1× `attendance_payroll_preview` (опционально draft rules) |
| Утвердить переработку | 1× status update |
| Сохранить типы отметок | 1× `attendance_replace_punch_types` |
| Экспорт | 1× по кнопке |

## Коротко одной схемой

```
Не участник → 0 запросов, ничего не видит

Admin: Сервисы → компания
         → настройки / работники / дежурные / отсутствия / OT / ЗП / табель / аналитика
         → invite и правила только через чат

Worker: accept в чате → Профиль «Посещаемость»
         → хаб → punch | мои детали
         → sheet на Home из локального pending (без API)

Архив → детально ИЛИ повторный invite в чат → снова «Ожидают»

Сеть: punch offline → outbox; invite/ack только online
Сессии: mobile = одна; web = параллельно (см. authentication)
```
